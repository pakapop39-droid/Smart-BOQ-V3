# แผนเติมแท็กและเลิกทำในแอปหลัก
วันที่ 23 ตุลาคม 2569 · สถานะ: แผนเพื่อทบทวนก่อนลงโค้ด · ยังไม่เปลี่ยนฐานหรือเชื่อมออนไลน์

## 1. เป้าหมายและขอบเขต
นำความสามารถที่ตกลงและเคยลองใน /trial.html มาทำในแอป SQLite หลัก / ให้ข้อมูลอยู่หลัง refresh/reopen ใช้การคำนวณและ snapshot เดิม ไม่ย้ายข้อมูลเบราว์เซอร์เข้า SQLite เงียบ ๆ ไม่เปิด cloud และไม่แก้หน้าราคาหรือเพิ่ม hierarchy เหนือ Keyplan

undo ต้นทุนรอบแรกหมายถึง component_cost_lines ของโครงการ ไม่ย้อนการลบ rate_template_cost_lines หรือรุ่น READY ในคลังต้นแบบ การขยาย undo ไปการลบระดับอื่นต้องวางขอบเขตแยกก่อน

รอบแรกครอบคลุมทะเบียนแท็ก ค้นหา/กรองข้ามสามคลัง bulk tag actions/export เลือกเพิ่มต้นทุนหลายรายการ ลบต้นทุนหลายแถว และเลิกทำการลบแท็ก/ต้นทุน ไม่รวม undo ราคาทุกครั้ง ลบทั้งโครงการ ย้อน migration/restore หรือเปลี่ยนรุ่นต้นแบบอัตโนมัติ

## 2. แบบข้อมูลที่เสนอ — ต้องยืนยันก่อนสร้างจริง
เสนอเพิ่ม resource_tags และ resource_tag_links สองตาราง เพื่อเก็บตัวตนแท็กและความสัมพันธ์หลายต่อหลายอย่างตรวจด้วย FK ได้ ไม่ซ่อนชื่อซ้ำในข้อความหรือใช้ cost_groups/work_categories ผิดหน้าที่ ถ้าอนุมัติ จำนวนธุรกิจในเฟสนี้จะเป็น 24 จากปัจจุบัน 22 ไม่ใช่มี 24 แล้วและไม่ถือว่ามาสเตอร์บังคับว่าทุกเฟสต้องคง 22 ตลอดไป

- resource_tags: UUID, company_id, name, normalized_name, sort_order, version, created_at/updated_at; unique(company_id, normalized_name) ใช้ NFC+trim ไม่เปลี่ยนความหมายตัวอักษรเอง
- resource_tag_links: UUID, tag_id, resource_id, company_id, version/เวลา; unique(tag_id,resource_id); FK/ownership ต้องอยู่บริษัทเดียวกัน
- cost_resources.tags ข้อความเดิมกลายเป็นช่อง compatibility สำหรับ Excel/ข้อมูลเก่า ชื่อปัจจุบันคำนวณจากทะเบียน ไม่เก็บสองแหล่งให้แก้ต่างกัน
- เก็บ undo journal เป็น metadata ของบริษัทใน JSON data ของ companies ที่ SQLite ปัจจุบันรองรับอยู่ ไม่เพิ่มตารางธุรกิจเพื่อปุ่ม UI และไม่แสดงเป็นช่องให้ผู้ใช้แก้ในฟอร์มบริษัท บันทึก journal กับคำสั่งลบ/คืนใน transaction เดียว
- รายการ journal มี command UUID, scope company/project/component, เวลา, ชนิดคำสั่ง, snapshot แถวที่ลบทั้งหมด, ตำแหน่งเดิม และ version ของแถวที่เกี่ยวข้องหลังคำสั่ง ไม่เก็บฐานทั้งก้อนและไม่เก็บ credentials; undo ห้ามคืนข้อมูล companies ทั้งแถวทับลำดับ RT/ข้อมูลบริษัทล่าสุด ต้องแก้เฉพาะ journal metadata ที่เกี่ยวข้อง

จุดต้องรับรองก่อนเริ่ม implementation: เจ้าของเห็นชอบการเพิ่มสองตารางและแผนย้ายข้อมูล/backup รุ่นใหม่ หากยังไม่อนุมัติ ให้คง 22 ตารางและทำได้เฉพาะต้นแบบแยก ห้ามแอบแทนทะเบียนจริงด้วยข้อความแล้วอ้างว่าครบ

## 3. ย้ายข้อมูลในเครื่องโดยเก็บข้อมูลเดิม
1. สำรอง SQLite ก่อน migration และตรวจ schema/FK/ยอดโครงการ baseline
2. preview การแยกข้อความ tags เดิมด้วยขึ้นบรรทัดใหม่ รองรับทั้งสามคลัง ตัดว่าง รวมชื่อซ้ำหลัง NFC+trim ภายในบริษัท ไม่อนุมานแท็กจากสินค้า หมวดงาน หรือขอบเขตต้นทุน
3. เมื่อยืนยันจึงสร้าง tags/links เก็บ UUID ของวัสดุ/งาน/ต้นทุน/รุ่นและราคาคงเดิมทั้งชุดใน transaction ถ้าผิดพลาด rollback ไม่ลบบางส่วน
4. ไม่ import localStorage จาก /trial.html อัตโนมัติ หากจะใช้ข้อมูลจากต้นแบบให้เลือกส่งออก/นำเข้าเองและตรวจตัวตนก่อน
5. backup รุ่นใหม่เสนอ SMART_BOQ_LOCAL_24_V1 ครบทะเบียนแท็กและ journal; รับไฟล์เดิม 18/22 โดยย้าย tags ข้อความอย่างมี preview สำรองฐานก่อนแทนข้อมูล ไม่เรียกไฟล์ 24 ตารางว่า backup 22 ตาราง
6. คืนฐานก่อน migration ด้วยไฟล์สำรองเท่านั้น ไม่ใช้ปุ่มเลิกทำทั่วไปย้อน schema และไม่ย้อนทับข้อมูลใหม่โดยไม่แจ้ง

## 4. หน้าจอและพฤติกรรม
### คลังและแท็ก
- แยกมุมมองวัสดุ / ค่าแรง / VS Modular ในคลังเดียวกัน ระบุ Modular จากรายละเอียด modular_products ไม่เหมาว่าสินค้าชุด BUNDLE ทุกตัวเป็น Modular และไม่เดาจากรหัส b เพียงอย่างเดียว ข้างซ้ายแสดงแท็กและจำนวนของคลังที่เลือก ด้านบนค้นหารหัส/ชื่อ
- หลายแท็กเป็น OR แล้ว AND กับคำค้น มีทั้งหมดและยังไม่ติดแท็ก การย้ายรายการระหว่างแท็กคือเอาแท็กออก/ติดแท็กเพิ่ม ไม่ย้ายประเภทต้นทุน
- checkbox หน้ารายการ + เลือกทั้งหมดเฉพาะผลที่แสดงและเลือกได้ แสดงจำนวน ยกเลิกได้ เปลี่ยน filter/คำค้น/คลังล้าง selection
- bulk เพิ่มแท็ก/เอาแท็กออก/ส่งออกที่เลือก การแก้ชื่อหรือรวมแท็กไม่กระทบราคา หน่วย snapshot และโครงการที่เคยใช้
- จัดการแท็กเพิ่ม/เปลี่ยนชื่อ/รวมเข้าปลายทาง/ลบเฉพาะแท็ก ชื่อซ้ำเสนอ “รวมแท็ก” แทน การลบแสดงจำนวน link ที่จะเอาออกก่อนยืนยัน วัสดุไม่ถูกลบ
- การรวมแท็กเป็นคำสั่งเฉพาะ มี preview และยืนยัน แต่ปุ่ม “เลิกทำการลบ” รอบแรกไม่ย้อนการรวม ต้องแสดงให้ตรง ไม่ใช้ป้ายเหมือน Ctrl+Z ทุกชนิด

### เลือกต้นทุนและลบ
- picker ในรายการทำราคาใช้คลัง/ตัวกรองเดียวกัน เลือกหลายรายการแล้วเพิ่มครั้งเดียว ตรวจทุกแถวก่อน commit
- แถวที่มีแล้วตามกติกาปัจจุบันแสดงเพิ่มแล้ว/ปิดเลือก ห้ามเหมารวมว่ารหัสเดียวกันห้ามใช้ต่างกลุ่มหรือคนละตำแหน่ง เพราะหลายบรรทัดในงานอาจอ้าง resource เดียวกันได้
- ห้ามใส่หินของ S002 กลับในต้นทุนตู้ด้วยการเลือก bulk หรือฝืนจำนวน Modular ที่ต้องเป็นเต็มชุด
- checkbox เลือก CHARGEABLE ในกลุ่ม/รายการที่กำลังดูเท่านั้น INCLUDED/EXCLUDED_REFERENCE เลือกเป็นรายการคิดเงินหรือลบเดี่ยวไม่ได้
- ลบที่เลือกครอบคลุมแม่สินค้าชุดกับ reference และ coverage ที่ต้องลบตามกัน แสดงผลกระทบก่อนทำ เก็บ raw snapshot ราคา/จำนวน/variant ตำแหน่งและข้ออ้างอิงครบ ไม่ลบวัสดุกลางหรือ project_resources ที่ยังใช้อยู่
- ถ้า reference ของรายการอื่นชี้บรรทัดที่กำลังลบ ให้ใช้กฎเดิม: ค้างการพิจารณาใหม่หรือบล็อกอย่างมีข้อความ ไม่สร้างอุปกรณ์ซ้ำเพื่อให้ยอดผ่าน
- สำเร็จแล้ว refresh state และคำนวณจากแกนเดิมทันที หากงานไม่ครบให้แสดงรอข้อมูล ไม่ยืนยันศูนย์เป็นต้นทุนจริง

## 5. API/transaction และ undo
เพิ่ม local endpoints โดยคง /api/local เดิม ไม่เพิ่ม cloud SDK:
- GET /tags?kind=… พร้อมจำนวน, POST /tags, PATCH /tags/:id
- POST /tags/merge พร้อม source/target version
- DELETE /tags/:id พร้อม expected version, บันทึก snapshot tag+links สำหรับ undo
- POST /tags/bulk ให้ resource_ids, tag_ids, action ADD/REMOVE และ expected versions
- POST /cost-lines/bulk-add และ POST /cost-lines/bulk-delete ให้ scope/group/component/project version และรายการ UUID/เวอร์ชัน ตรวจเจ้าของทุกแถวก่อนแก้
- GET /undo/latest?scope=… และ POST /undo/:commandId พร้อม current expected versions

ทุก mutation ผ่าน local ownership/version/FK และ SQLite transaction คำสั่งใดผิดให้คืนทั้งหมด ไม่ให้ API /records ทั่วไปข้าม journal/validation สำหรับ tag/cost delete ได้

undo ใช้คำสั่งลบล่าสุดที่ยังคืนได้ตาม scope คืน UUID เดิม เนื้อหาเดิม ตำแหน่ง/แม่ลูก/coverage และชื่อแท็ก/link เดิมโดยไม่สร้างซ้ำ ไม่คืน version เก่าลงทับปัจจุบัน ให้เพิ่ม version ใหม่และล้างหลักฐานยืนยันเพิ่มเติมที่ไม่ตรงข้อมูลปัจจุบันตามกฎเดิม

ถ้า UUID/ชื่อแท็ก/ความเป็นเจ้าของ/เวอร์ชันที่ต้องใช้คืนเปลี่ยนไป ให้บล็อก undo ทั้งชุดพร้อมเหตุผล ไม่คืนครึ่งชุด ไม่ rollback ทั้งฐานหรือคลังล่าสุด เมื่อสำเร็จ mark command ว่าใช้แล้วใน transaction เดียวและคำนวณใหม่ ประวัติคงอยู่หลังเปิดใหม่ได้

ไม่บันทึก selection/filter ชั่วคราวเป็นข้อมูลธุรกิจ และไม่ใช้ journal แทนการสำรองฐาน ยอด/ราคาใช้โมดูลคำนวณเดิม ไม่เขียนสูตร UI ชุดใหม่

## 6. Excel และการสำรอง
- คงแม่แบบ 1/2 ได้เพื่ออ่านไฟล์เก่า: v1 ไม่มี tags ไม่ล้าง; v2 ใช้ชื่อแยกบรรทัด ช่องว่างล้าง เฉพาะแถวที่มีในไฟล์
- tag ID ภายในไม่สร้างเป็นวัสดุใหม่ ส่งออกชื่อปัจจุบันจากทะเบียน หากชื่อในไฟล์ไม่รู้จักให้ preview รายชื่อแท็กที่จะสร้างก่อนยืนยัน ไม่มี side effect ตอน preview
- เปลี่ยนชื่อแท็กต้องเพิ่ม resource version ของรายการที่ export เปลี่ยน ให้ไฟล์เก่าที่แก้ข้อมูลแล้วชนตรวจ conflict ได้ ไม่ถือชื่อเก่าว่าเป็น alias ที่ต้องสร้างกลับเองโดยเงียบ ๆ
- คงการจับคู่ ID/version, no-op ไม่เพิ่มรุ่น, missing row ไม่ลบ, import atomic และไม่เปลี่ยน snapshot งานเดิม
- ทดสอบ backup/restore รายละเอียด undo ด้วย ถ้ารุ่นเก่าไม่มีก็เป็นประวัติว่างอย่างชัดเจน

## 7. ลำดับส่งมอบและเกณฑ์รับ
1. อนุมัติแบบ 24 ตาราง/preview ย้ายข้อมูล → migration local + fixture/backup tests โดยยังไม่แตะข้อมูลจริง
2. tag registry + CRUD/merge/delete/undo และ OR filter → ตรวจวัสดุเดียวมีหลายแท็กข้ามสามคลัง ไม่ซ้ำ ไม่เปลี่ยนราคา
3. bulk tagging/export + picker เพิ่มหลายต้นทุน → ตรวจ selection แถวซ่อน รหัสเดิม การเลือกต่างกลุ่ม และ rollback เมื่อหนึ่งแถวผิด
4. bulk delete + persistent undo → ตรวจลบชุดแม่+reference+coverage คืนครบตำแหน่งและยอดหลัง refresh/reopen รวม stale/conflict
5. Excel v1/v2 และ backup 18/22/24 → ตรวจ no-op/ชื่อใหม่/ล้างแท็ก/เปลี่ยนชื่อ/ไฟล์เก่า/ข้อมูลผิด; โครงการเดิมยังยอดเดิม
6. รัน regression ทั้งหมดและ build ตรวจหน้าหลักจริง / ไม่ใช้ผล /trial.html แทน ส่งลิงก์ในเครื่องพร้อมขั้นตอนให้เจ้าของลอง ก่อนอนุมัติเชื่อมออนไลน์แยกภายหลัง

ฐานรับรอง: ชุดเดิมในเครื่อง 125 cases ต้องผ่านต่อ และเพิ่ม tests ที่ตรวจผลจริง ไม่ตั้งเป้าจำนวน tests เป็นหลักฐานว่าฟีเจอร์ครบ ไม่มีการถือแผนนี้ว่า migration ได้ติดตั้งแล้ว
